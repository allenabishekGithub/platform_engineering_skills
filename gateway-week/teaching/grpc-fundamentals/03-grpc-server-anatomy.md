# 03 — Anatomy of a real gRPC server: `mock-grpcServer`

The sample you will mimic. `nafmock` is the mock NAF/TFS platform built for
this assignment (real, tested, in this repo) — and its shape is exactly the
shape your gateway server should have. Read this with the source open:

```
mock-grpcServer/
  api/nafmock/v1/nafmock.proto      contract
  api/nafmock/v1/nafmock.pb.go      generated (never edit)
  api/nafmock/v1/nafmock_grpc.pb.go generated (never edit)
  internal/server/server.go         the service implementation  <- mimic this
  internal/server/behavior.go       domain logic
  internal/server/admin.go          HTTP side-car
  internal/server/server_test.go    bufconn tests
  cmd/nafmock/main.go               wiring: listen, register, shutdown
```

Generated vs. hand-written is the first lesson: **everything under `api/` is
regenerated by `make generate`; all your code lives elsewhere.**

## Layer 1 — the contract (nafmock.proto)

Unary, deliberately generic: `ApplyOperation(operation string, payload bytes)`.
One rpc, two messages. It models the platform as "apply this named operation
with this opaque payload" — which is all your gateway needs to know.
Your gateway's `api/gateway/v1/gateway.proto` differs only in vocabulary.

## Layer 2 — the service struct (server.go)

The pattern to copy verbatim into your gateway:

```go
type Server struct {
    nafmockv1.UnimplementedNAFMockServer   // embed: forward compat

    mu              sync.Mutex             // your own state
    defaultBehavior Behavior
    history         []HistoryEntry

    executions *prometheus.CounterVec     // instruments as fields
    ...
}
```

Why embed `Unimplemented...`: the generated interface grows if you add rpcs
later. The embedded type returns `Unimplemented` for any method you didn't
write, so the interface keeps compiling. It is not optional politeness; it
is the mechanism that keeps contract evolution survivable.

Why state in the struct: gRPC spawns a goroutine per call, and calls arrive
concurrently — everything your handler touches must live on the server struct
behind a mutex (or be a store, like your gateway's SQLite).

## Layer 3 — the handler (server.go, ApplyOperation)

The shape — memorize it:

```go
func (s *Server) ApplyOperation(ctx context.Context,
    req *nafmockv1.ApplyOperationRequest)      // 1. ctx is ALWAYS first
    (*nafmockv1.ApplyOperationResponse, error) { // 2. return (msg, error)

    md, _ := metadata.FromIncomingContext(ctx)   // 3. read metadata
    ...                                          // 4. do the work

    if failed {
        return nil, status.Error(codes.Unavailable,
            fmt.Sprintf("nafmock behavior %q", raw))  // 5. errors = status
    }
    return &nafmockv1.ApplyOperationResponse{   // 6. success = filled msg
        Handle: handle, Echo: req.GetPayload(),
    }, nil
}
```

The five idioms this handler demonstrates:

1. **ctx first, ctx always.** It carries the caller's deadline and
   cancellation. `waitCtx(ctx, d)` inside — every blocking operation is
   ctx-aware, which is the whole reason `delay:` / `hang:` behaviors work.
   `nafmock` hangs until the *caller's* deadline, not its own timer.
2. **Getters, not field access**: `req.GetPayload()` — nil-safe. Fields
   would panic on a nil message.
3. **Metadata in**: behavior override (`nafmock-behavior`) and correlation
   ID (`x-correlation-id`) arrive via metadata, lowercase keys — exactly how
   your gateway receives `idempotency-key`.
4. **status.Error for failures** — code for machines, message for humans.
   Note it maps ctx errors itself: `codeFromCtxErr` turns
   `context.DeadlineExceeded` into `codes.DeadlineExceeded`. Your gateway
   inherits that requirement.
5. **Ground truth counters** (`nafmock_executions_total`) increment only
   where the side effect actually happens — not per request. That
   distinction (requests vs. executions) is the entire evidence strategy
   for "duplicates execute once."

## Layer 4 — the wiring (cmd/nafmock/main.go)

Read top to bottom; it is ~80 lines and shows the canonical lifecycle:

1. `flag` parsing — ports and default behavior, so demo scenarios are flags.
2. `slog.New(slog.NewJSONHandler(...))` — structured logs from line one.
3. Constructor with validation that can fail (`New` returns error).
4. `grpc.NewServer()` → `RegisterNAFMockServer` → register **health** +
   **reflection** — the two standard add-ons from file 01.
5. Separate HTTP mux for `/metrics`, `/healthz`, admin — gRPC and HTTP on
   different listeners/ports. Your gateway does the same (:50051 / :9090).
6. `signal.NotifyContext` → on signal: `GracefulStop()` with a timeout —
   the graceful-shutdown pattern from flowd ex1, applied to a gRPC server.
7. Health set to SERVING only once serving — never before.

## Layer 5 — the test harness (server_test.go)

The thing to steal for your gateway's integration tests:

```go
lis := bufconn.Listen(1 << 20)                  // in-memory listener
grpcServer := grpc.NewServer()
RegisterNAFMockServer(grpcServer, srv)          // the real server, no mocks!
go grpcServer.Serve(lis)

conn, _ := grpc.NewClient("passthrough:///bufnet",
    grpc.WithContextDialer(dial lis.DialContext), // route the conn to bufconn
    grpc.WithTransportCredentials(insecure.NewCredentials()))
```

Why this is the gold standard: interceptors, metadata, deadlines, status
mapping — the *entire* gRPC machinery runs, over a pipe instead of TCP.
Tests spin up a real server per test with a fresh store, then exercise
scenarios (see `TestBehaviorMatrix` — a table of behaviors × expected codes
× expected execution counts). Your Friday failure matrix is this file's idea
applied to the gateway.

## What your gateway does differently (and same)

| Aspect | nafmock (platform) | your gateway |
| --- | --- | --- |
| Service struct + embed Unimplemented | same | same |
| Handler signature, status codes, metadata | same | same |
| State | in-memory counters | **SQLite-persisted operation records** |
| Decisions | behavior tokens (deliberately dumb) | state machine + idempotency + retry policy |
| Interceptors | none | correlation ID, logging, metrics |
| Executor | none — it IS the execution | wraps *this very server* |

Run it and talk to it before writing your own (file 04): the fastest way to
make layers 1-4 concrete is to be the client of a server whose source you
have read.
